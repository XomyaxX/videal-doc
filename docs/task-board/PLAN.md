# Доска рабочих задач

Страница для закрытого теста. Это не производственные задачи шотов (`Task` в пайплайне). Новые таблицы только добавляются. Старые таблицы и их данные не меняются.

Доска живёт на `/board`. Пока переменная `WORK_BOARD` не равна `1`, страницы нет ни в меню, ни по адресу. Когда флаг включён, страница открыта только роли `superadmin`. Боевой сервер этим изменением не выкатывается: деплой по-прежнему отдельно и только после команды владельца.

## Модель

### Задача `WorkBoardTask`

| Поле | Смысл |
|---|---|
| `title`, `body` | Название и описание. У карточки сотрудника название — «Отдел — имя», описание — должность и доступы, если они есть в базе |
| `status` | `todo` (к выполнению), `wip` (в работе), `done` (готово). «Готово» ставится в любом порядке, связи его не блокируют |
| `assigneeId` | Сотрудник из `User`. Пусто — никто не назначен |
| `staffUserId` | Если карточка заведена скриптом на человека, здесь его id. Повторный сид такую карточку не переписывает |
| `departmentId` | Отдел для области на схеме и провала внутрь. Пусто — группа «Без отдела» |
| `dueOn` | Срок, строка `ГГГГ-ММ-ДД`, пустая если срока нет. Раньше сегодняшнего дня по Москве и статус не «готово» — просрочка |
| `prodTaskId` | Необязательная ссылка на производственную задачу `Task`. Удаление шота обнуляет ссылку, саму задачу не трогает |
| `authorId` | Кто создал. При удалении пользователя поле обнуляется |
| `posX`, `posY` | Место на общей схеме |
| `sortOrder` | Порядок шагов. Считает сервер |
| `version` | Номер правки. Чужая правка с устаревшим номером получает ответ 409 |
| `deletedAt` | Мягкое удаление |

Исполнителем нельзя поставить человека со `status = dismissed` или с заполненным `deletedAt`. Если человека уволили уже после назначения, карточка продолжает его показывать, но в списке выбора его нет, и повторно назначить нельзя.

### Связь `WorkBoardEdge`

Ребро всегда хранится как «ранняя задача → поздняя задача» (`fromId` → `toId`). Одна пара в одну сторону — одна связь.

| `kind` | Жест на схеме | Как читается стрелка |
|---|---|---|
| `blocks` | От мешающей задачи к той, которую она блокирует | «блокирует» |
| `depends` | От зависимой задачи к той, которая ей нужна | Стрелка разворачивается: нужная задача указывает на зависимую, подпись «нужна для» |
| `sequence` | От предыдущего шага к следующему | «далее» |

Все три вида одинаково участвуют в порядке и в проверке цикла. Петля на себя запрещена. Новое ребро запрещено, если из конца уже можно дойти до начала по существующим рёбрам. Проверка делается в транзакции вместе со вставкой, плюс уникальный ключ `(fromId, toId)` на случай двух одновременных запросов.

После добавления или снятия связи сервер заново раскладывает `sortOrder` устойчивой топологической сортировкой: рёбра задают «раньше / позже», задачи без рёбер остаются в прежнем относительном порядке, шаг номера — 10. Если в данных уже оказался цикл, порядок не переписывается.

Удаление карточки снимает её связи и помечает `deletedAt`. Строки производственных задач не правятся: на них только необязательная ссылка.

Отдельного поля «обязанности» в таблицах сотрудников нет. Скрипт `npm run seed:work-board` читает работающих (`deletedAt` пустой и `status` не `dismissed`) и создаёт карточки. В описание попадает только то, что уже лежит в базе: название должности (`Position.name`), человекочитаемые доступы из `Role.permissions` и дополнительные отделы. Если должности нет, строка не пишется, зелёное поле остаётся пустым и его можно заполнить руками. Скрипт не обновляет `User`, `Role`, `Department` и `Task`. Повторный запуск не затирает уже созданные карточки.

### Миграция

`prisma/migrations/20261110120000_work_board/migration.sql` создаёт две новые таблицы. `prisma/migrations/20261110150000_work_board_dept_due/migration.sql` добавляет к `WorkBoardTask` столбцы отдела, сотрудника, срока и производственной задачи. На старые таблицы нет правок строк. Локально схема накатывается `prisma db push`. На офисной базе SQL применяют отдельно, когда владелец разрешит выкладку, и затем один раз `npm run seed:work-board`.

Внешние ключи на `User` стоят с `ON DELETE SET NULL` и висят на новых таблицах. Удаление сотрудника по-прежнему удаляет строку `User`. Если у него были карточки доски, у карточек просто очистится автор или исполнитель.

## Экраны

Доска одна на всю студию.

1. **Схема.** Тёмная сетка. Карточка: жёлтый заголовок, зелёное описание. Люди одного отдела стоят в общей области с жёлтым ярлыком. Нажатие на ярлык проваливает схему в этот отдел; «Вся студия» возвращает общий вид. Связи прежние: «блокирует», «зависит от», «дальше». На карточке срок и необязательная производственная задача. Просрочка обводится красным. «Готово» не зависит от связей.
2. **Статусы.** Три колонки внутри текущего отдела или по всей студии.
3. **Люди.** Колонки исполнителей. Уволенного назначить нельзя.

На карточках в колонках виден шаг порядка и имена задач, которых она ждёт.

## Одновременная правка

В приложении нет общего websocket-канала. Чат уже опрашивает сервер раз в несколько секунд, база — один SQLite на офисном сервере. Для теста этого достаточно:

- клиент шлёт маленькую правку и номер `version`;
- сервер обновляет строку только если номер совпал, затем увеличивает его;
- если номер устарел, ответ 409 и свежий снимок доски;
- каждые 4 секунды клиент забирает снимок, пока пользователь не тащит карточку;
- положение на схеме в журнал не пишется на каждый пиксель, чтобы не забить аудит.

На фазе P1, если доской будут пользоваться одновременно больше нескольких человек, тот же снимок можно отдавать через SSE, без Redis и без второго сервиса.

## Права и журнал

Закрытый тест: `WORK_BOARD=1` и роль `superadmin`. Остальные получают ту же пустую страницу, что и при выключенном флаге (`notFound`), пункт меню им не показывается. API при выключенном флаге отвечает 404, при включённом и чужой роли — 403.

В существующий `AuditLog` пишутся действия `workboard.create`, `workboard.update`, `workboard.delete`, `workboard.link`, `workboard.unlink`. Сущность — `workboard_task` или `workboard_edge`. Сдвиг карточки по холсту в журнал не попадает.

Позже, когда владелец откроет доску студии, право лучше завести отдельным кодом вроде `workboard.use`, а не раздавать всем через роль суперадмина. В этом прототипе новый код права не добавлялся, чтобы не трогать редактор ролей.

## Фазы

### P0 — этот прототип

Готово, когда суперадмин при `WORK_BOARD=1` может:

- открыть `/board` и не увидеть её без флага или без роли;
- создать, переименовать, описать и удалить карточку;
- назначить работающего сотрудника и не назначить уволенного;
- поставить статус «к выполнению», «в работе», «готово» в любом порядке, в том числе если предыдущий шаг ещё не готов;
- подвинуть карточку по сетке, и место сохранится после обновления страницы;
- провести связь трёх видов, увидеть подпись и анимацию стрелки;
- получить отказ, если связь замыкает цикл или повторяет уже существующую;
- увидеть тот же порядок в номерах шагов;
- править доску одновременно с другим суперадмином без тихого затирания текста: чужая версия возвращает 409 и свежие данные;
- видеть одну схему студии, области отделов и провал внутрь отдела;
- видеть карточки всех работающих после `npm run seed:work-board`;
- ставить срок и видеть просрочку;
- при желании связать карточку с производственной задачей.

Закрытый тест смотрит только суперадмин. Подписи связей остаются «блокирует», «зависит от», «дальше».

Критерий приёмки по коду: `npm test` проходит, `npm run build` проходит. `npm run lint` на этом репозитории уже красный из-за старых файлов; новые файлы доски линтер не ругает.

### P1 — после закрытого теста, если владельцу зайдёт

- Открыть доску выбранным ролям, не только суперадмину.
- Оценка часов и фильтр «мои».
- Уведомление исполнителю, когда предыдущий шаг стал «готово» или срок просрочен.
- Отмена последнего действия.
- Лента изменений вместо опроса раз в 4 секунды.

### P2 — если понадобится планирование по времени

- Диаграмма Ганта на MIT-библиотеке frappe-gantt поверх тех же сроков и рёбер.
- Шаблоны цепочек (аниматик → черновик → чистовик).
- Комментарий на карточке.

## Риски

- Пакет `@xyflow/react` увеличивает клиентский бандл только страницы доски. Остальные маршруты его не грузят, компонент клиентский.
- Два человека, тянущие одну карточку, получат победу последнего удачного `version`. Текст при этом не теряется молча.
- Жест «зависит от» разворачивает стрелку. На экране есть подсказка, но это легко перепутать. Если владельцу удобнее, чтобы стрелка всегда шла туда, куда тянули, тип связи можно хранить отдельно от направления.
- Пустые таблицы на боевой базе безвредны, но появляться там должны только вместе с выкладкой, которую делает владелец. Этот прототип сам ничего не выкладывает.
- Флаг по умолчанию выключен в `.env.example`. Если на офисе переменную не задать, доски не будет даже у суперадмина.

## Решения владельца

1. Доска одна на студию, с провалом в отдел.
2. «Готово» можно ставить в любом порядке, блокировки нет.
3. Закрытый тест смотрит только суперадмин. На доску заносятся все работающие сотрудники.
4. Срок есть на карточке, просрочка подсвечивается.
5. Карточку можно связать с производственной задачей, ссылка необязательная.
6. Подписи связей не переименовываем.
